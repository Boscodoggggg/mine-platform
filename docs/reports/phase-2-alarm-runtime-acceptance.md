## 1. 结论摘要

本切片把告警从路线图字段推进为可配置、可运行、可追溯、可人工处置的纵向闭环。管理员可在产品、设备组和单设备三级作用域配置数值阈值或数据质量命中规则；Telemetry 原子加载最后正确镜像，只对通过持久最新值顺序判定的实时帧推进状态，并把触发/恢复事实与遥测、质量证据和 Outbox 同事务提交。

告警事件通过 RabbitMQ publisher confirm 可靠发布，Server 使用独立最小权限账号和 Inbox 幂等聚合同一告警周期。触发与恢复可以乱序，确认与恢复互相正交，只有已恢复告警可以关闭。Web 端已经具备规则编辑、有效配置、默认未关闭视图、筛选、完整证据详情、确认和关闭。

真实设备、厂商报文、矿区网络、阈值调优、短信/电话/企业 IM/工单送达、值班响应、容量、HA、备份恢复、故障注入和 24/72 小时长稳按当前要求未执行。本报告只能证明仓库实现和自动化集成基线，不能作为矿区上线签字或对外销售终验凭证。

## 3. 关键运行不变量

1. `ALARM.rules` 是原子覆盖字段；设备组或设备覆盖父级完整规则集合，不做隐式逐条合并。
2. Telemetry 只对持久最新值顺序状态接受的实时帧推进告警；补传、旧 boot 和低序号不制造实时告警风暴。
3. 缺值、`BAD`、`TIME_UNTRUSTED` 或未实际执行到的质量规则是 `UNKNOWN`，不会被误判为恢复。
4. 状态、遥测事实和告警 Outbox 同事务提交；publisher confirm 前不得标记事件已发布。
5. 损坏、低修订或同修订异内容不会覆盖最后正确策略镜像。
6. 规则删除、禁用或语义变化会可靠恢复旧活动周期并记录明确原因。
7. Server 允许触发与恢复乱序，但不允许同一周期的身份、时间或证据互相冲突。
8. 确认和恢复是正交事实；关闭只能发生在恢复之后，重复处置不重复写事实或成功审计。
9. 指标标签不得包含设备、产品、规则、告警周期、快照、事件或异常文本。

## 5. 数据库、消息与升级边界

管理服务 V25 开放 `ALARM` 策略和运行快照，V26 创建 `alarm_event`、`alarm_acknowledgement` 及告警菜单/权限。Telemetry V12 创建告警最后正确镜像，V13 创建持久状态机和可靠 Outbox，V14 补充未完成事件索引。所有新增表和字段都有中文注释，数据库集成测试校验注释完整。

消息契约版本为 1，稳定事件类型为 `alarm.raised` 和 `alarm.recovered`，业务聚合键为 UUIDv7 `alarmOccurrenceId`。Telemetry 账号只新增 `mine.business.x` 写权限；`mine-server-alarm` 只读取 `mine.server.alarm-event.q`，不获得无关交换机和队列权限。

迁移只向前执行。应用回退前必须验证旧版本能容忍新表和新消息；业务策略回退通过更高发布事实完成，不回滚 Flyway，不删除运行水位、Inbox、Outbox 或告警周期，不手工覆盖 Telemetry 镜像。

## 6. 明确延期项

- 厂商真实设备、真实报文、矿区时钟源、弱网和补传链路；
- 各产品/设备族阈值、误报率、漏报率、触发/恢复持续和冷却参数调优；
- 短信、电话、企业 IM、邮件、工单、升级策略、送达回执和值班响应演练；
- `DEAD` 告警 Outbox 的受权查询、原因修复、重放/补偿 API 与操作审计；当前版本只有告警和证据保留，不允许改库重放；
- 更多规则来源、窗口统计、跨属性组合、告警关联、抑制编排和维护窗口；
- 5000 MQTT、UWB 峰值、重连风暴、告警风暴和 RabbitMQ 积压恢复；
- 双 Telemetry/Server、一致性追赶、数据库主备、备份恢复、断电和跨节点故障；
- 安全渗透、生产密钥托管、24/72 小时稳定性和正式上线签字。

## 7. 下一步建议

1. 按 Phase 2 路线图先实现 `RETENTION` 受控保留策略：影响预览、按 chunk 清理、限速、进度、失败恢复、审计和不可删除数据边界。
2. 在保留事实稳定后实现 `AGGREGATION` 聚合/派生策略，明确迟到修正、质量合并、重算和查询契约。
3. 再推进 TCP/二进制协议 SPI 与一个可复现纵向样例，避免平台长期只覆盖 MQTT JSON。
4. 通知渠道实现可以并行设计，但真实送达和值班升级必须留在独立现场验收，不与当前仓库自动化结论混淆。

# 12 开发路线与 Codex 工作流

## 1. 总体策略

项目按纵向闭环交付，不按前端、后端、数据库横向割裂。每个阶段结束时必须能够部署、演示、测试和回滚。

~~~mermaid
flowchart LR
    P0["阶段0 工程底座"] --> P1["阶段1 真实设备闭环"]
    P1 --> P2["阶段2 协议与策略平台"]
    P2 --> P3["阶段3 智慧矿山业务"]
    P3 --> P4["阶段4 现场生产加固"]
~~~

## 2. 阶段 0：工程底座

### 目标

一条命令启动空平台，能够登录、鉴权、查看健康状态并连接基础中间件。

### 范围

- Maven 多模块父工程和前端工程。
- Spring Boot 4、统一 BOM、代码格式和静态检查。
- mine-common、mine-device-model、mine-messaging 基础类型。
- mine-server 启动、Sa-Token、五表 RBAC、Flyway。
- RabbitMQ 双 vhost、Redis、PostgreSQL、TimescaleDB。
- mine-web 登录、动态路由、请求层。
- 单机 Compose。
- 基础 Prometheus、日志和 traceId。
- CI 构建、单测、类型检查、SBOM。

### 退出标准

- clean checkout 可离线/受控联网构建。
- compose-standalone 启动健康。
- 超级管理员首次登录和修改密码。
- 无权限 API 返回标准 403。
- Flyway 可从空库创建。
- 所有服务有健康检查和版本信息。

## 3. 阶段 1：最小设备闭环

### 目标

用一种真实 MQTT 设备和一个模拟器打通上报、存储、实时展示、历史查询和命令 ACK。

### 范围

- 产品、设备和凭据。
- 统一设备消息 v1。
- MQTT topic ACL。
- gateway 消费设备 vhost 并发布内部事件。
- telemetry 幂等、映射、Redis 最新值和 Timescale 数值历史。
- WebSocket RealtimeHub。
- 动态设备监控最小版。
- 一个命令模板、状态机和设备模拟 ACK。
- 基础弱网重复/乱序/补传。

### 退出标准

- 真实设备连续运行 24 小时。
- 重复 QoS1 不重复产生历史副作用。
- 迟到补传不覆盖最新值。
- 页面断线重连后先快照再增量。
- 命令区分 Broker 接收和设备执行。
- 对应集成和 E2E 测试通过。

## 4. 阶段 2：协议与策略平台

### 目标

普通新设备可以在不修改 Java、不重启服务的情况下配置接入。

### 范围

- 协议定义、字段、样本和调试器。
- 物模型属性/事件/命令。
- 字段映射和数据质量。
- 配置包、作用范围、继承、冲突和有效配置。
- 发布、节点加载、回滚和审计。
- 告警、在线离线、保留、聚合和弱网策略。
- Java 协议 SDK 和一个示例插件。

### 退出标准

- 至少三种差异化报文通过配置接入。
- 黄金样本发布门禁可阻止破坏性变更。
- 运行节点热切换完整快照。
- 加载失败保留 last-known-good。
- 同优先级组冲突被阻止。
- 配置发布/回滚 E2E 通过。

### 当前实施状态（2026-07-17）

| 能力 | 状态 | 边界 |
|---|---|---|
| MQTT JSON 协议、黄金样本、热发布与回滚 | 自动化通过 | 真实厂商报文、双 Gateway 和现场恢复延期 |
| 产品/设备组/单设备三级有效值 | 自动化通过 | 已证明继承、逐字段来源和同级冲突阻断 |
| 设备组与历史成员关系 | 自动化通过 | 已证明乐观锁、生命周期和数据库约束 |
| 在线离线策略运行消费 | 自动化通过 | 当前仅 `offlineThresholdSeconds`，本机缓存与 last-known-good 已接入 |
| 数据质量策略运行消费 | 自动化通过 | 已覆盖时间、必填、数值上下限、逐属性质量、同事务证据、可靠分发和本地最后正确镜像；现场阈值调优延期 |
| 策略工作台 | 自动化通过 | 在线状态/数据质量/告警切换、告警双来源规则、复制排序、原子覆盖、有效值、中英文、主题治理、权限、发布和回滚已覆盖 |
| Gateway 失败证据、指标与告警 | 自动化通过 | 告警送达、值班响应和现场故障演练延期 |
| Telemetry 策略分发与质量告警 | 自动化通过 | 永久失败、持续重试和质量突增规则已配置；告警送达和值班演练延期 |
| 双来源告警运行与处置闭环 | 自动化通过 | 持久状态机、可靠 Outbox、乱序聚合、确认/关闭、前端中心、审计、权限和监控已覆盖；真实阈值、通知送达和值班演练延期 |
| 保留、聚合和弱网策略 | DEFERRED | 尚未进入各自运行消费者，不能标记为完成 |
| TCP/二进制协议和示例插件 | DEFERRED | MQTT JSON 之外尚未形成生产实现 |
| 真实设备、容量、HA 与 24/72 小时长稳 | DEFERRED | 按当前计划留待现场与生产加固阶段 |

本表的“自动化通过”只表示仓库代码、契约和容器化集成门禁通过，不等于矿区生产放行。Phase 2 只有在剩余策略消费者和协议类型完成后才能整体关闭；Phase 4 现场门禁未完成前，项目不能宣称已经取得生产上线资格。

## 5. 阶段 3：智慧矿山业务

### 目标

设备数据能够形成车辆、人员、路线、UWB、作业、命令和告警业务闭环。

### 范围

- 车辆、人员和司机资质。
- 设备/标签/人员/车辆时间绑定。
- 路线、途径点和围栏。
- UWB 专用流水线、轨迹和实时位置。
- 班次、作业单、运营记录和统计。
- 告警确认/恢复。
- 通讯菜单和命令历史。
- Cesium 基础三维场景、演示模型和降级。

### 退出标准

- 历史位置按发生时绑定关联正确对象。
- 自动途径点/围栏事件可重放且幂等。
- 一次完整作业可自动/人工闭环。
- 三维故障不影响核心管理页面。
- 页面覆盖用户提供截图中的核心能力。

## 6. 阶段 4：生产加固

### 目标

获得矿区现场上线资格。

### 范围

- 五节点 Compose 和故障切换手册。
- 离线安装、升级、回滚和镜像签名/校验。
- WAL/基础备份和恢复。
- 全套监控、告警和巡检。
- 5000 MQTT 客户端与 UWB 峰值压测。
- 弱网和故障注入。
- 72 小时稳定性。
- 安全、SBOM、许可证和漏洞处置。

### 退出标准

10-testing-quality-gates.md 的现场上线门禁全部通过并形成报告。

## 7. 每个功能的完成定义

一个功能只有同时满足以下条件才算完成：

- 需求/验收条件已写清。
- API、消息或数据库契约已更新。
- 先有失败测试，再有实现。
- 单元、集成和必要 E2E 通过。
- 权限码、审计和错误码已实现。
- 指标、日志和告警已补。
- 部署配置和 migration 已补。
- 中文 Javadoc 符合 AGENTS.md。
- 文档和示例已更新。
- 使用中文 Conventional Commit。

## 8. Codex 单任务模板

每次只交付一个可验证闭环：

~~~markdown
目标：
实现设备创建 API，不包含凭据轮换。

必须阅读：
- AGENTS.md
- docs/02-repository-backend.md
- docs/08-security-auth-audit.md
- docs/11-contracts-and-database.md

允许修改：
- mine-server device 模块
- 对应 migration 和测试
- OpenAPI 文档

验收：
- 未登录 401
- 缺少 device:device:create 为 403
- 编码重复为 409
- 正常创建为 201
- 操作审计写入

禁止：
- 修改其他模块 Mapper
- 使用 H2
- 跳过失败测试
~~~

## 9. Codex 执行顺序

1. 阅读 AGENTS.md 和专题文档。
2. 检查 git status 和现有测试。
3. 将任务拆成 2–5 分钟动作。
4. 写最小失败测试并运行确认失败原因正确。
5. 写最小实现。
6. 运行针对测试。
7. 运行模块测试和架构规则。
8. 更新契约/文档。
9. 检查 diff，不混入无关改动。
10. 中文提交。

禁止一次提示同时要求“把所有模块全写完”。复杂功能按 schema、后端、前端、E2E 和文档分步，但每步保持可运行。

## 10. 任务切片建议

合适：

- 增加一个 migration 和 Repository。
- 增加一个 API 及权限/审计测试。
- 增加一个消息类型和消费者幂等。
- 增加一个协议字段类型及黄金样本。
- 增加一个前端列表页和 E2E。

过大：

- 完成整个协议中心。
- 完成智慧矿山全部业务。
- 一次生成所有数据库表和全部页面。

过小：

- 只创建空类而没有测试/行为。
- 只改 DTO 名称但不更新契约。

## 11. 代码评审清单

### 通用

- 是否满足明确验收，而非仅能编译。
- 是否引入不需要的抽象和依赖。
- 是否改变公共契约。
- 是否包含 secret、真实报文或个人数据。

### 后端

- Controller 是否越过 Service 调 Mapper。
- 事务边界是否正确。
- 异步消息是否幂等。
- 时间使用 occurredAt 还是 receivedAt 是否明确。
- 中文 Javadoc 是否解释边界。

### 前端

- 权限是否只做展示而未依赖其安全性。
- 高频数据是否误入 Pinia。
- 断线/加载/空/错误状态是否完整。
- 动态 schema 是否有白名单和降级。

### 数据/运维

- migration 是否可升级。
- 队列、缓存和任务是否有上限。
- 是否新增指标和告警。
- 是否更新备份和恢复影响。

## 12. 分支与提交

建议：

- main：随时可发布。
- feature/{scope}-{short-name}：短生命周期功能分支。
- release/{version}：仅在确有现场发布维护需要时创建。

提交示例：

~~~text
feat(device): 新增设备创建与编码唯一性校验
test(protocol): 增加长度字段粘包回归样本
fix(telemetry): 修复迟到消息覆盖最新值
docs(deploy): 补充单机恢复流程
~~~

## 13. 变更治理

以下变更先写 ADR：

- 增加新基础中间件。
- 拆分/合并运行服务。
- 改变消息信封或数据库主键策略。
- 改变权限模型。
- 允许脚本执行或插件热加载。
- 从 Compose 迁移到其他编排。
- 改变开源许可证。

## 14. 阶段报告

每阶段输出：

- 功能清单和未完成项。
- API/消息/schema 版本。
- 测试与覆盖率。
- 性能和资源数据。
- 已知限制。
- 升级和回滚方法。
- 下一阶段风险。

没有报告和可复现构建，不进入下一阶段。

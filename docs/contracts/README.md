# 契约目录

本目录保存需要跨模块、跨进程或跨团队稳定解释的数据契约。契约文件进入版本控制，已发布版本不得原地改变语义；不兼容变更必须新增版本文件并提供迁移说明。

| 文件 | 用途 | 生产者 | 消费者 |
|---|---|---|---|
| `message-envelope-v1.json` | 平台内部 RabbitMQ 统一消息信封示例 | gateway、telemetry、server | 所有消息消费者 |
| `phase-1-device-acceptance-v1.schema.json` | 首台真实 MQTT 设备 24 小时验收证据 JSON Schema | 现场接入与运维人员 | 评审、发布门禁和后续自动化工具 |

验收 Schema 的约束重点：

- `PASS` 验收窗口至少 24 小时且至少由两名责任人批准；三个自动化门禁必须通过，必须有真实遥测、真实断线恢复、成功命令终态及关键证据，不能存在未关闭或仅接受的高危问题。提前失败的记录保留实际运行时长。
- 消息、失败、未知报文、断线和序列缺口必须给出绝对计数。
- 流量和延迟必须记录分布；无流量时使用 `null`，不得用 0 冒充测量结果。
- 证据只保存受控路径与 SHA-256，不把明文凭据或未经脱敏的生产报文提交仓库。
- `BLOCKED` 只要求公共门禁、问题和证据，不强迫伪造设备、观察窗口或遥测；必须填写含非空白字符的外部阻塞原因。它不是 `PASS` 或 `FAIL` 的替代写法。

JSON Schema 只负责结构和一部分明显的跨字段放行约束，不能证明证据真实，也不能完成日期算术和矿区阈值判断。发布门禁的语义校验器还必须确认 `startedAt < endedAt`、两者时间差与 `durationHours` 一致，并按已批准基线检查失败率、延迟、积压恢复和资源水位。现场签字、原始指标、日志、命令时间线和消息样本仍需按运行手册留存。

# 聚合策略运行时设计

## 1. 目标与边界

本批为 `AGGREGATION` 策略建立真实运行消费者，而不是只在策略工作台增加一个表单。平台需要按产品、设备组和单设备三级最终有效策略，把数值遥测物化为可长期查询的固定时间桶，并明确迟到数据、质量合并、重算、分页快照和数据保留顺序。

首版只处理 `telemetry_numeric`，固定生成 `AVG`、`MIN`、`MAX`、样本数、桶内最差质量和最晚接收时间。不提供任意表达式、自由 SQL、用户自定义函数、跨设备公式、UWB 轨迹降采样或对象存储归档。派生指标将在聚合事实稳定后作为后续独立切片接入，因此本批完成前不得把 Phase 2 的“聚合/派生”整体标记完成。

真实矿区数据、容量、HA、备份恢复和长时间稳定性继续延期；本批只形成仓库自动化和容器化数据库证据。

## 2. 方案选择

候选方案有三种：

1. 查询时临时聚合：实现简单，现有历史接口已经支持，但原始数据清理后无法支撑长期查询，也没有运行审计和覆盖水位。
2. TimescaleDB 连续聚合：运维代码较少，但会把核心语义绑定到扩展版本与许可能力，迟到修正、重算审计和多级策略覆盖仍需额外控制面。
3. 平台自管有界物化：由 Telemetry 使用数据库单实例锁、固定批次和不可变执行事实生成聚合版本，可独立验证、限速、重放和降级。

采用方案 3。它与现有数据保留任务、最后正确策略镜像、可靠策略分发和 Apache 模式 TimescaleDB 基线一致，代价是平台需要维护调度器、执行事实、覆盖水位与查询选择逻辑。

## 3. 策略契约

`AGGREGATION` 顶层只允许一个原子 `policy` 对象：

```json
{
  "policy": {
    "enabled": true,
    "correctionWindowSeconds": 86400,
    "rules": [
      { "propertyId": "speed", "bucketSeconds": 300 },
      { "propertyId": "payload", "bucketSeconds": 3600 }
    ]
  }
}
```

约束如下：

- `enabled` 必填且必须为布尔值。
- `correctionWindowSeconds` 必须为 300 到 604800 秒。
- `rules` 为 1 到 100 条原子规则；`propertyId` 使用物模型标识白名单格式。
- `bucketSeconds` 只允许 `60、300、900、3600、21600、86400`。
- 同一 `propertyId + bucketSeconds` 不得重复；修正窗口不得小于规则最大桶宽的两倍。
- 规范化结果按属性标识和桶宽稳定排序，保证控制面与 Telemetry 独立计算相同哈希。

规则集合在三级作用域中整体覆盖，避免不同作用域拼接出未经管理员审核的组合。

## 4. 数据流与原子边界

发布、回滚、设备组成员变化、设备归档和组优先级变化继续通过现有不可变运行快照与 RabbitMQ 轻量事件分发。Telemetry 分页拉取完整快照，使用共享 `AggregationStrategyDefinition` 独立校验并暂存，随后在一个事务中切换 `telemetry_aggregation_policy` 最后正确镜像、推进独立运行修订水位并记录 Inbox。

聚合调度器与数据保留调度器使用不同 advisory lock，单轮执行有最大规则数、最大桶数和超时。执行器只处理已经闭合的桶：桶结束时间必须早于数据库当前时间减去该设备策略的修正窗口。这样窗口内到达的弱网数据会在首次物化时自然被包含，不需要反复覆盖未闭合桶。

每次常规物化或显式重算都写入新聚合版本，不能原地篡改已经对查询可见的版本。版本携带源摄取水位、策略运行修订、策略快照和内容哈希；同一源水位和策略语义重试必须幂等。单批聚合版本与执行进度在同一事务提交，失败批次回滚后可以安全重试。

## 5. 数据模型与查询一致性

Telemetry 新增三类事实：

- `telemetry_aggregation_policy`：逐设备最后正确策略镜像。
- `telemetry_numeric_rollup`：按设备、属性、桶宽、桶起点和聚合版本保存统计值。
- `telemetry_aggregation_execution`：保存 `RUNNING/SUCCEEDED/PARTIAL/FAILED`、实例、策略数、生成桶数、源水位和脱敏错误。

聚合版本使用单调 `rollup_revision`。历史接口首页同时返回原始摄取 `watermark` 和聚合 `rollupWatermark`；后续页必须原样传回。每个桶选择不超过两个水位的最新版本，因此后台重算不会让同一次分页前后看到不同事实。

查询采用冷热拼接：已经闭合并物化的完整桶读取 rollup，仍在修正窗口内的桶读取原始数据；跨越边界时后端合并、稳定排序后分页。请求桶宽必须与生效规则一致才能读取长期 rollup；不一致的请求只能在原始数据仍存在时临时计算，并明确返回数据来源。

## 6. 迟到、重算与保留顺序

修正窗口内的迟到数据在桶首次闭合时自动纳入。超过窗口的迟到数据不能静默改写历史；平台记录固定低基数指标，并允许具备治理权限的管理员按设备、属性和有界时间范围创建显式重算。重算产生更高聚合水位的新版本和审计事实，旧版本至少保留到查询会话上限之后再清理。

原始数据清理必须满足两组条件：既达到 `RETENTION` 天数，又已存在覆盖该行所属规则和时间桶的成功聚合版本，且桶已越过修正窗口。没有聚合策略的属性继续沿用原保留规则；有聚合策略但覆盖缺失时 fail closed，保留原始行并暴露阻塞指标。执行顺序固定为“先聚合、后保留”，不能用调度时间碰巧先后替代数据库覆盖检查。

## 7. 安全、故障与可观测性

策略管理复用 `device:strategy:view/edit/publish`，重算额外使用 `governance:aggregation:execute`；查询继续使用 `device:telemetry:view`。页面不得接受 SQL、表名、函数名或任意表达式。所有写操作记录操作审计与幂等键。

快照解码、哈希、暂存或激活失败时保留 last-known-good。聚合任务数据库不可用时记录失败执行事实和脱敏错误，不删除原始数据；超过失联阈值的 `RUNNING` 由后续实例收敛。Prometheus 仅使用 `status、operation、dataset` 等固定标签，禁止设备、产品、属性和错误文本成为标签。

核心告警包括连续失败、连续部分完成、执行失联、聚合覆盖落后、因覆盖缺失阻塞保留和超窗口迟到增长。前端必须展示加载、空、错误、禁用、影响范围和最后执行状态，并遵守现有主题与国际化治理。

## 8. 自动化验收

- 共享定义对合法策略产生稳定规范化结果，拒绝未知字段、重复规则、非法桶宽和过短修正窗口。
- PostgreSQL/TimescaleDB 迁移包含中文表注释及全部字段注释，并由集成测试逐项校验。
- 控制面发布、回滚和生命周期变化能够生成 `AGGREGATION` 快照；Telemetry 能原子激活、删除和防止修订倒退。
- 有界执行、锁竞争、迟到窗口、显式重算、失败回滚、执行事实和指标均有自动化测试。
- 历史查询在冷热边界、分页水位和后台重算期间保持稳定；保留任务不会越过聚合覆盖。
- 前端双语、权限、主题治理、单元测试、构建和 Chromium E2E 通过。
- 验收报告明确自动化与真实现场验证边界。

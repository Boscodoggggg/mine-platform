# Phase 2 受控数据保留策略运行闭环设计

## 1. 目标与范围

本切片在现有三级策略控制面、可靠运行快照和 TimescaleDB 遥测存储上交付 `RETENTION` 纵向闭环：管理员按产品、设备组或设备配置保留等级，发布前查看影响预览，Telemetry 原子加载最后正确策略并以单实例、有界批次清理过期数据，平台展示执行历史、进度与失败原因。

首版只治理 `telemetry_numeric` 原始数值遥测和 `telemetry_quality_evidence` 质量证据。保留年龄以平台可信 `received_at` / `created_at` 计算；原始遥测同时使用 hypertable 时间列限制候选 chunk，避免设备伪造旧时间导致刚入库数据被立刻删除。

以下事实不在首版删除边界内：`telemetry_alarm_runtime_state`、告警 Outbox、持久最新值、`telemetry_inbox`、策略镜像与修订水位、服务端告警事件和操作审计。位置轨迹尚未形成 Phase 3 业务归属，也不在本切片中伪装为已治理能力。真实容量、现场长稳、备份恢复、HA 和生产数据清理演练继续延期。

## 2. 方案选择

### 方案 A：TimescaleDB 全局保留策略

原生策略简单高效，但当前多个产品和设备共享 hypertable，无法表达产品、设备组和设备的不同保留期。直接 `drop_chunks` 会越权删除仍在保留期的数据，因此不采用。

### 方案 B：有效策略分组后的 chunk 可裁剪批量删除

控制面继续产生单设备最终有效策略，Telemetry 使用类型化本地镜像。执行器按数据库时间、策略天数和 chunk 时间边界选择候选行，每批有固定上限；删除失败可安全重试，策略回滚无需恢复已删数据但会立即阻止后续错误删除。采用该方案。

### 方案 C：按保留等级拆分 hypertable

大规模生产下物理分层更高效，但需要改写写入、查询、迁移和冷热存储拓扑。首版先积累真实分布与执行证据，后续在不改变 `RETENTION` 契约的前提下演进。

## 3. 受控策略契约

策略类型为 `RETENTION`，只开放原子字段 `policy`。产品、设备组和单设备覆盖时替换整个对象，不对内部字段做跨作用域拼接：

~~~json
{
  "policy": {
    "enabled": true,
    "retentionClass": "STANDARD",
    "rawTelemetryDays": 90,
    "qualityEvidenceDays": 180
  }
}
~~~

约束如下：

| 字段 | 约束 | 语义 |
|---|---|---|
| `enabled` | 布尔值 | `false` 时保留镜像但执行器跳过，便于安全暂停和回滚 |
| `retentionClass` | `SHORT/STANDARD/LONG/ARCHIVE` | 面向运营与报价的稳定保留等级 |
| `rawTelemetryDays` | 7～3650 且符合等级区间 | 原始数值遥测最短平台留存天数 |
| `qualityEvidenceDays` | 不小于原始天数且不超过 3650 | 质量违规证据留存天数 |

原始天数区间分别为 `SHORT 7～30`、`STANDARD 31～180`、`LONG 181～730`、`ARCHIVE 731～3650`。对象拒绝未知字段、缺字段、浮点天数和不一致等级。工作台提供 7/30、90/180、365/730、1825/3650 四组默认值，但允许在等级边界内调整。

## 4. 运行镜像与删除执行

控制面将 `RETENTION` 纳入不可变增量快照；Telemetry 使用共享类型注册表重新校验，再原子写入 `telemetry_retention_policy`。镜像保留原始 JSON、内容哈希、快照和修订号，并用生成列暴露启用状态、等级和天数，避免执行 SQL 依赖不受控 JSON 转换。

执行器使用数据库会话级 advisory lock，保证同一 TimescaleDB 只有一个保留任务工作。每次运行先创建 `telemetry_retention_execution` 事实，再按数据集执行最多配置数量的批次。每批只删除配置上限内的主键候选并立即提交；达到本轮上限记为 `PARTIAL`，下轮从剩余事实继续，全部扫描完成记为 `SUCCEEDED`。进程崩溃会释放数据库锁，超时的 `RUNNING` 事实由下一实例收敛为 `FAILED`。

删除天然幂等，不保存脆弱的行游标；失败批次未提交，下次重新扫描即可恢复。执行记录包含实例、状态、策略数、删除行数、批次数、开始/完成时间和脱敏截断错误。终态事实不允许删除，避免人为抹除运维证据。

## 5. 影响预览与管理接口

`mine-server` 复用独立 TimescaleDB 只读账号提供：

- `POST /api/v1/retention-previews`：校验 `policy` 和目标作用域，返回受影响设备数、各数据集达到删除条件的行数、最早时间和是否达到统计上限；预览只读且使用数据库当前时间。
- `GET /api/v1/retention-executions`：查询最近执行事实，返回状态、进度、删除量和失败摘要。

接口复用 `device:strategy:view`，策略发布仍要求 `device:strategy:publish` 并进入现有操作审计。预览不是删除承诺：从预览到策略激活期间数据仍会变化，页面必须显示统计时点和上限标记。

## 6. 可观测性、失败与回滚

Telemetry 暴露低基数运行次数、删除行数、运行中状态、最近成功时间和本轮是否未完成指标。Prometheus 对连续失败、长时间无成功和持续 `PARTIAL` 告警。日志只记录执行标识、状态和数量，不记录设备业务值。

发现误配置时先发布 `enabled=false` 或回滚到历史安全策略，确认 Telemetry 修订水位后再排障。保留删除不可逆，数据库备份恢复才是恢复已删事实的唯一手段；因此现场生产放行前必须补充备份恢复演练和真实数据 dry-run，本切片的容器化自动测试不能替代这些门禁。

## 7. 自动化验收

- 类型注册表拒绝未知字段、越界天数、等级错配和证据天数短于原始数据。
- 产品、组、设备继承保持 `policy` 原子覆盖，同级冲突阻止发布。
- 快照损坏、低修订和同修订异内容保留最后正确镜像。
- 两个执行器竞争时只有一个获得锁；批次有界、失败可重试、暂停策略不删除。
- 只删除超过平台最短留存且属于启用策略设备的原始遥测和质量证据，保护边界表保持不变。
- 新表及全部字段具备中文注释，并由 TimescaleDB 集成测试校验。
- 预览、执行历史、权限、前端中英文、主题治理、单元、集成和浏览器 E2E 通过。

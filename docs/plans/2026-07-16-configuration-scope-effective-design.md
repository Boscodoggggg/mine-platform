# 配置作用域与有效配置设计

## 1. 目标与本批边界

本批关闭阶段 2 的“产品默认、设备组覆盖、单设备覆盖”继承和同优先级冲突门禁，让管理员能够明确回答某台设备当前为什么使用某个配置值。实现必须适合 5000 台以上设备，控制面可以查询数据库和计算影响，设备消息热路径不得逐条查库或解释任意 JSON。

继承顺序固定为：

```text
产品默认 < 设备组优先级 0..1000 < 单设备覆盖
```

设备同时属于多个组时，数值更大的组优先级覆盖数值更小的组。同优先级组可以提供不同字段，也可以为同一字段提供相同值；若为同一字段提供不同值，发布或成员关系变更必须返回 `STRATEGY-409-001`，不能依赖数据库返回顺序决定结果。

第一种真正接入现有业务的策略为 `ONLINE_STATUS`，首个字段是 `offlineThresholdSeconds`。设备接入状态优先读取有效策略；尚未发布策略时继续使用现有连接配置阈值，保证升级不改变既有设备行为。真实设备、现场网络、容量和长稳验证按用户决定暂缓，但自动化、权限、审计、迁移和可观测性不能因此省略。

本批不允许设备组或单设备覆盖协议解析定义。当前 Gateway 仍以产品作为协议兼容边界；如果不同设备使用不兼容报文，应拆分产品。后续只有在设备级完整快照和数据面内存索引完成后，才开放协议作用域覆盖。

## 2. 方案比较与选择

### 方案 A：最高作用域整包覆盖

实现简单，但设备组配置一个字段就会覆盖整个产品包，无法满足“未配置字段继续继承”，也容易把协议、物模型和策略错误混用，因此拒绝。

### 方案 B：设备消息到达时实时查询并合并

能够即时反映配置，但会把 PostgreSQL 和 JSON 合并放进采集热路径。控制面故障将直接影响数据面，且 5000 台设备下延迟和数据库压力不可接受，因此拒绝。

### 方案 C：不可变作用域片段加确定性解析器

选用此方案。草稿保存经过类型注册表校验的局部字段；发布形成不可变版本和作用域发布事实。控制面解析器按固定优先级合并，并返回最终值、逐字段来源和冲突列表。运行消费者只使用已解析的不可变结果或本地缓存，不在热路径读取草稿。

策略定义采用后端白名单注册表，不提供脚本、SpEL、SQL、正则表达式或任意函数。JSON 只作为存储和 API 表达，领域层必须先转换为已知字段和类型再参与计算。

## 3. 数据模型

新增 `dev_device_group`：

- 归属一个产品，包含稳定 `group_key`、中英文无关的业务名称、0..1000 优先级、状态和乐观锁版本。
- 产品内 `group_key` 唯一；归档组不参与当前有效配置。
- 修改优先级属于高影响写操作，必须先验证全部受影响设备不存在同优先级冲突，再使用乐观锁更新并记录审计。

新增 `dev_device_group_membership`：

- 记录设备、组、生效时间和失效时间，不物理删除历史关系。
- 设备和组必须属于同一产品；同一设备与组只能存在一条当前有效关系。
- 加组前对该设备执行冲突预检；移组通过关闭生效区间表达。

新增 `dev_strategy_version`：

- 归属产品和策略类型，保存局部 `values`、规范化 SHA-256、`DRAFT/PUBLISHED` 状态、版本号和乐观锁版本。
- 草稿允许更新；发布版本不可更新或删除。
- `ONLINE_STATUS.offlineThresholdSeconds` 范围为 1..604800，未知字段、空对象、超限对象和错误类型均在服务端拒绝。

新增 `dev_strategy_release`：

- 引用已发布策略版本，作用域为 `PRODUCT/GROUP/DEVICE`，保存作用域标识、原因、幂等键、发布人和产品内单调序号。
- 发布事实只增不改；回滚通过发布历史版本形成更高序号事实。
- 每个作用域和策略类型以最高发布序号作为当前值，历史始终可追溯。

所有新增表和字段使用 PostgreSQL `COMMENT ON TABLE/COLUMN` 中文注释，迁移集成测试校验注释、约束、索引和不可变触发器。

## 4. 有效配置算法

解析器输入是一个产品片段、零到多个设备组片段和零或一个设备片段。每个片段已经过策略类型校验，算法不接受未知字段。

1. 写入产品默认值，来源标记为产品发布。
2. 按组优先级升序处理组片段。
3. 同优先级先按字段聚合；同字段出现多个不同规范化值时产生冲突，整个结果无效。
4. 无冲突时覆盖低优先级值，并记录组、优先级和发布标识。
5. 最后应用单设备值并记录来源。
6. 对最终对象再次执行跨字段校验并计算规范化哈希。

结果包含 `values`、`sources`、`contentHash` 和 `conflicts`。来源至少包含作用域类型、作用域标识、发布标识和组优先级。返回顺序稳定，哈希不受数据库查询顺序或 JSON 对象字段顺序影响。

发布组策略、改变组优先级或新增组成员前，服务端必须对所有受影响设备运行解析器。任何冲突使整个写操作失败，不允许只跳过冲突设备。产品策略和单设备策略不会形成同级冲突，但仍要经过类型和最终值校验。

## 5. API、权限与前端

设备组 API：

- `GET/POST /api/v1/device-groups`
- `PUT /api/v1/device-groups/{id}`
- `POST /api/v1/device-groups/{id}/archive`
- `PUT /api/v1/device-groups/{id}/members`

策略 API：

- `GET/POST /api/v1/strategy-versions`
- `PUT /api/v1/strategy-versions/{id}`
- `POST /api/v1/strategy-versions/{id}/publish`
- `POST /api/v1/strategy-releases`
- `GET /api/v1/devices/{id}/effective-strategies/{strategyType}`

权限拆分为设备组查看/编辑、策略查看/编辑/发布。所有写操作由后端强制鉴权，发布要求原因和 `Idempotency-Key`；成功写操作记录前后摘要，不记录完整敏感配置或凭据。409 冲突返回稳定错误码和逐字段 `violations`。

前端策略工作台按“产品/设备组/设备作用范围、策略编辑、有效值与来源”三栏组织。用户可见文案全部国际化，使用 Naive UI 和 UnoCSS，不引入页面私有样式或硬编码颜色。冲突必须展示涉及字段、设备和组，不只显示笼统失败消息。

## 6. 运行时、缓存与升级兼容

`DeviceAccessStatusService` 通过只读 `EffectiveOnlineStatusPolicyProvider` 批量获取阈值。没有有效策略、策略服务暂不可用或升级前数据为空时，回退到现有 `DeviceConnectionProfile.offlineThresholdSeconds`；已发布但损坏的策略不得静默回退，必须暴露错误并保持上一份已知良好结果。

第一批可以在 Server 进程内使用按设备和策略类型索引的有界缓存，发布和成员变更按受影响设备精确失效。缓存只保存解析后的不可变对象，数据库仍是控制面事实源。后续 Gateway/Telemetry 消费策略时，由控制面生成包含有效策略的完整产品快照并沿现有 Outbox 发布，不允许消费者自行查询多张控制面表。

迁移不改写现有连接配置。上线新版本后，没有策略发布的设备行为与升级前一致，便于增量部署和回滚。

## 7. 可观测性、失败处理与测试

新增指标至少包括有效配置解析次数与结果、冲突字段数、解析耗时、缓存命中/失效、策略发布结果。标签只使用策略类型和结果等低基数字段，禁止把 deviceId、groupId 或 releaseId 放进指标标签。

日志携带 traceId、策略类型、作用域和发布标识，冲突日志只记录字段路径和标识，不记录整份策略 JSON。数据库失败返回标准 5xx，乐观锁和同级冲突返回 409，类型或范围错误返回 422。

自动化覆盖：

- 纯 Java 解析器的继承、优先级、相同值合并、同级冲突、稳定哈希和输入上限。
- 数据库表/字段中文注释、跨产品关系、有效区间、索引和不可变约束。
- 服务层权限、审计、幂等、乐观锁、影响设备冲突预检和历史回滚。
- 接入状态服务使用有效阈值及无策略兼容回退。
- 前端有效值来源、冲突展示、权限按钮、主题与国际化治理。
- 后端全量验证、前端 typecheck/lint/unit/build 和不依赖真实设备的浏览器契约 E2E。

真实设备 24 小时、现场网络、双节点故障、5000 连接压测和 72 小时长稳仍保留在生产放行清单，不在本批自动化通过后伪造为已完成。

# Phase 1 弱网补传自动化验证报告

> 验证日期：2026-07-15
>
> 验证分支：`feat/phase-0-foundation`
>
> 验证范围：MQTT 设备模拟场景、遥测消费、TimescaleDB 历史、PostgreSQL 持久最新值、Redis 最新值、设备序列缺口指标和实时事件
>
> 当前结论：**Task 15 自动化弱网验证通过；真实矿区网络和真实设备长稳运行仍需 Task 16 现场验收**

## 1. 验证目标

本轮验证固定以下弱网序列，确保任何开发机和 CI 环境都能重复执行：

1. `weak-boot-a` 正常上报序号 1、2、3。
2. 序号 3 使用同一事件标识重复投递。
3. MQTT 主动优雅断开 600,000ms，模拟设备离线 10 分钟。
4. 恢复后先上报序号 7，确认序号 4、5、6 暂时缺失；随后重复投递相同的序号 7 事件，再乱序补传 4、5、6。
5. 继续上报序号 8。
6. 设备重启为 `weak-boot-b`，MQTT 重新连接，序号从 1 开始。
7. 新启动周期上报到序号 2 后，再补传旧 `weak-boot-a` 的序号 9。

场景唯一事实源为 `examples/device-simulator/scenarios/weak-network.yaml`。模拟器测试与遥测端到端测试均读取该文件，避免维护两份序列造成漂移。模拟器自动化测试使用虚拟等待，直接运行 JAR 时会按配置执行 Paho 优雅断开并等待。它不覆盖链路骤断、半开连接、KeepAlive 超时、丢包、抖动或 QoS 在途重投，因此只能作为弱网处理逻辑的确定性基线，不能替代网络代理故障注入和矿区现场验收。

## 2. 自动化分层

弱网验证分为两层：

- 模拟器层：校验 YAML 能编译为稳定的断线、重启和遥测步骤；精确验证 `断开 -> 等待 600,000ms -> 连接 -> 订阅 -> 上报序号 7`，以及 `断开 -> 连接 -> 订阅 -> weak-boot-b/1` 的顺序。
- 遥测层：把 YAML 描述的标准化报文逐条交给真实消费者，使用 Testcontainers TimescaleDB 和 Redis 检查持久化、最新值、幂等、序列缺口和实时发布。

遥测层从 gateway 已完成身份校验和标准化后的消息开始，不在同一个测试进程内重复验证 MQTT 鉴权与厂商报文解析；这些边界分别由 gateway MQTT 集成测试和设备凭据集成测试覆盖。

## 3. 实测结果

| 指标 | 结果 | 验收含义 |
|---|---:|---|
| 输入报文 | 13 帧 | 含 2 帧完全重复、4 帧补传、1 次重启 |
| 唯一持久事件 | 11 个 | 重复事件没有生成第二条 Inbox 记录 |
| 数值历史点 | 22 个 | 每个唯一事件 2 个属性，历史无丢失 |
| PostgreSQL 最新值 | 2 个属性 | 值、`bootId`、`sequence`、`eventId` 均来自 `weak-boot-b/2` |
| Redis 最新值 | `engine.rpm=2002` | `bootId=weak-boot-b`、`sequence=2` |
| 退役启动周期 | 1 个 | `weak-boot-a` 已记录为退役周期 |
| 设备序列缺口事件 | 1 次 | `weak-boot-a` 从 3 到 7，暂缺 4、5、6 |
| 缺失设备序号计数 | 3 个 | 对应指标 `mine.telemetry.sequence.gap.missing` |
| RabbitMQ 手工确认 | 13 次 ACK | 无 NACK、无不可重试 Reject |
| 实时发布调用 | 9 次 | 实时通道为至少一次语义，幂等重投保留相同事件标识 |

## 4. 核心断言

- 重复序号 3 使用相同 UUIDv7，`telemetry_inbox` 和历史表只写一次。
- 序号 7 基于数据库加锁后的设备持久顺序状态产生且只产生一个缺口观察：前序为 3、当前为 7、暂缺 3 个序号；随后重复投递同一个序号 7 事件，缺口指标仍然只有一次。
- 设备序号契约允许从 0 开始，真实数据库集成测试覆盖 `0 -> 2` 并确认缺口为 1，不会因边界校验失败形成永久重投。
- 序号 4、5、6 虽晚于序号 7 到达，仍完整写入历史，但不覆盖最新值，也不发布错误的最新值事件。
- `weak-boot-b` 可以从序号 1 重新开始，并淘汰旧启动周期的最新值资格。
- 重启后补传的 `weak-boot-a/9` 即使设备发生时间更晚，也只能进入历史，不能把 PostgreSQL 或 Redis 最新值回退到旧启动周期。
- PostgreSQL 不只断言行数，还逐项核对 `engine.rpm=2002`、`vehicle.speed=20`、`bootId=weak-boot-b`、`sequence=2` 和对应事件标识。
- 实时发布是至少一次语义，重复投递可能再次发布相同 `eventId`；本阶段尚未实现告警和工单引擎，因此本报告不声称已验证告警、工单等未来业务副作用。

## 5. 两类“序号缺口”必须区分

设备报文的 `sequence` 用于判断同一 `bootId` 内是否暂缺设备数据。本轮新增的两个 Micrometer Counter 是：

- `mine.telemetry.sequence.gap.events`：设备序列缺口事件次数。
- `mine.telemetry.sequence.gap.missing`：缺失设备序号总数。

RealtimeHub 向浏览器发送的连接内 `sequence` 是另一套传输序号，由实时会话独立生成。浏览器是否触发 `RESYNC` 只能依据 WebSocket 连接序号或重连状态，不能因为设备报文从 3 跳到 7 就直接触发。因此，本轮只验证设备序列缺口指标，不把它冒充为 WebSocket 丢帧。

序列缺口指标是 best-effort 可观测性能力：指标注册器异常会被隔离，不能阻塞已持久化遥测或触发无效重投。未来如果告警、工单等业务需要可靠消费缺口事件，必须使用事务 Outbox，不得复用该指标观察器冒充可靠消息。

## 6. 执行命令

~~~bash
./mvnw -B -ntp -pl examples/device-simulator \
  -Dtest=ScenarioTest,SimulatorRuntimeTest test

./mvnw -B -ntp -pl mine-telemetry \
  -Dtest='*Test' -Dit.test=WeakNetworkE2EIT verify
~~~

本次定向执行结果：模拟器 8 个测试通过；`mine-telemetry` 25 个单元测试和 1 个弱网集成测试通过。完整模块验证另包含 8 个存储集成测试和 1 个迁移集成测试。

## 7. 尚未覆盖的现场风险

本报告不是矿区生产放行证明，以下项目必须在 Task 16 或后续生产加固阶段完成：

- 真实设备本地缓存容量、掉电保护、补传限速和磁盘写满行为。
- 井下真实网络的丢包率、抖动、蜂窝切换、基站盲区和重连风暴。
- RabbitMQ 持久队列积压水位、磁盘告警和恢复速率。
- 真实厂商 MQTT 报文、时钟漂移、`bootId` 生成规则和固件重启行为。
- 至少 24 小时真实设备连续运行，以及更长时间的平台长稳和资源增长观察。

在这些现场项目完成前，本轮结果只证明平台的确定性弱网处理逻辑和自动化回归基线通过。

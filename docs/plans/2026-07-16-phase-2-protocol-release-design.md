# 阶段 2 协议配置发布闭环设计

## 1. 目标与边界

第一批交付让普通 MQTT JSON 设备能够在不修改 Java、不重启服务的前提下接入平台。管理员维护物模型、协议字段、转换规则和黄金样本，测试通过后将它们组成不可变配置包并发布；Gateway 热加载完整快照后使用新规则解析报文，失败时继续使用 last-known-good。

本批必须用三组结构明显不同的 MQTT JSON 黄金样本证明配置化接入，包括扁平字段、嵌套字段以及枚举与数值换算。TCP/二进制帧、设备组和单设备覆盖、告警/保留/聚合策略、中高风险命令以及在线安装 Java 插件不在本批实现范围内，但数据模型和事件契约不得阻断后续扩展。

## 2. 总体架构

`mine-protocol-engine` 是无 Spring、无数据库依赖的纯 Java 内核，负责结构校验、JSON 路径读取、类型转换、白名单转换函数、物模型约束和样本回放。Server 和 Gateway 使用同一个编译器与执行器，避免“控制面测试通过、数据面解析不同”的双实现问题。

Server 是配置控制面，保存协议样本、测试结果、配置包和发布事实。配置包只引用已发布物模型和协议映射版本，保存规范化快照及 SHA-256；发布前重新运行全部黄金样本。发布和回滚都创建新的发布事实，回滚不修改历史版本。

Gateway 是数据面。发布事件只携带 releaseId、packageId、contentHash 和目标产品；Gateway 使用内部受权接口拉取完整快照，在内存中完成哈希、结构和本地编译校验，再原子替换产品快照。任何失败都不得覆盖当前快照，并要上报节点状态。

## 3. 协议模型与样本

第一批协议定义聚焦 MQTT JSON：

- `sourcePath` 使用受限点路径，例如 `data.engine.speed`，数组、通配符和脚本表达式暂不开放。
- 元数据路径分别声明 productKey、deviceCode、bootId、sequence、occurredAt 和 replayed；可信身份仍来自 MQTT Topic 与凭据快照，报文身份只用于一致性校验。
- 转换函数限定为 `NONE`、`SCALE`、`OFFSET`、`SCALE_OFFSET` 和 `ENUM`；现有 `EXPRESSION` 草稿不能进入配置包。
- 每条映射声明源类型、目标物模型属性、必填规则和失败质量行为。
- 黄金样本包含原始 JSON、期望成功/失败、期望统一属性或错误码。发布门禁必须全部通过，测试运行保存逐样本结果。

规范化快照采用稳定字段顺序和 UTF-8 JSON 生成 SHA-256。草稿允许修改；测试结果和已发布配置包不可变。样本失败、目标属性缺失、类型不兼容、重复目标字段、未知转换函数或快照哈希不一致都会阻止发布。

## 4. 发布、回滚与运行时

一次发布事务创建 `config_release` 和 outbox 事件。Gateway 收到事件后拉取快照并按“下载候选 → 校验哈希 → 编译候选 → 原子替换 → 上报状态”的顺序执行。相同 releaseId 与 hash 幂等；同一产品只接受更高的 release sequence；低版本或同版本异哈希被拒绝。

回滚选择历史配置包，但生成更高 release sequence 的新发布，因此节点仍只处理单调递增版本。Gateway 启动时优先读取本地最后成功快照，再向 Server 对账；控制面暂时不可用不阻断设备数据链路。本地文件只保存非敏感配置，不包含设备密码、内部令牌或 TLS 私钥。

节点上报 `PENDING`、`LOADED` 或 `FAILED`，包括节点 ID、releaseId、实际 hash、加载时间和脱敏错误摘要。控制面页面显示各节点结果，但不能因为单节点超时篡改已创建的发布事实。

## 5. 安全、可观测性与验收

管理接口使用独立的查看、编辑、测试、发布和回滚权限；发布/回滚要求原因、`Idempotency-Key` 和操作审计。内部快照接口只允许部署时注入的服务令牌，令牌不得进入数据库、日志或前端。单份定义、样本数、单样本字节数、字段数和路径深度都必须有上限。

核心指标包括协议解析成功/失败数、失败原因、当前 release sequence、快照加载结果与耗时。日志携带 productKey、releaseId 和 traceId，但不记录完整原始报文。

本批验收要求：三种差异 MQTT JSON 报文通过配置接入；破坏性修改被黄金样本阻止；Gateway 无重启切换快照；坏快照保留 last-known-good；回滚产生新发布并恢复旧行为；数据库中文表/字段注释、OpenAPI、权限、审计、后端测试、前端治理和 E2E 全部通过。

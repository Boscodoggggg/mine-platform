# Gateway 身份快照版本治理设计

## 1. 目标

Phase 1 继续以 `device-identities.json` 作为 gateway 的启动和现场兜底配置，但任何运行时入口都必须通过同一套版本治理规则，避免旧文件、重复发布或同版本篡改覆盖当前生效身份。

本次只治理身份快照的激活过程和运维可见性，不建设 Phase 2 的前台配置中心，不改变 MQTT 协议，不增加数据库表，也不增加新的定时扫表任务。

## 2. 生效规则

- 首个合法快照必须使用大于等于 1 的整数版本。
- 候选版本大于当前版本时，校验全部设备身份后原子生效。
- 候选版本等于当前版本且原始文件 SHA-256 相同时，视为幂等重复读取，不替换注册表。
- 候选版本等于当前版本但 SHA-256 不同时，拒绝并保留当前快照。
- 候选版本小于当前版本时，拒绝并保留当前快照。
- 业务回滚必须把旧内容发布为更高的新版本，不能降低版本号。

SHA-256 按文件原始字节计算，因此同版本下即使只改变空格或字段顺序也会被视为不同发布。这是有意的：现场发布记录、校验和与实际文件必须一一对应。

## 3. 组件边界

`DeviceIdentitySnapshotLoader` 负责一次性读取文件、计算摘要、解析 JSON 并构造候选身份；它不单独维护当前版本。

`DeviceSessionRegistry` 在一个 `AtomicReference` 中同时保存主题索引、设备索引、版本、摘要和设备数量。版本比较与原子替换在注册表内完成，使当前文件轮询入口和后续配置事件入口无法绕过单调保护，也避免运维读取到“新身份、旧版本”的中间状态。

注册表返回 `ACTIVATED` 或 `UNCHANGED`。所有解析、唯一性、版本和摘要校验都在替换前完成，失败不会修改 last-known-good。

gateway 通过现有内部管理端口 `/actuator/info` 增加 `deviceIdentitySnapshot` 明细，包含当前 `version`、`sha256` 和 `deviceCount`。该信息不通过业务端口或 Nginx 暴露，供现场运维、发布脚本和功能探针核对。

## 4. 失败与恢复

低版本、同版本异内容、非法 JSON、重复身份和字段错误均让本次 reload 失败，当前连接处理继续使用上一有效快照。启动时首个快照非法则 gateway RabbitMQ 配置不完成，避免在未知身份状态下接收设备消息。

同版本同摘要属于正常轮询，不记录为新发布。需要回滚时，发布人员复制已知良好的 `devices` 内容、递增 `version`、生成新 SHA-256，再按原子重命名流程发布。

## 5. 验证

- 单元测试覆盖首次激活、更高版本、同版本同摘要、同版本异摘要和低版本。
- 测试确认所有拒绝分支继续查询到原身份和原状态。
- 配置测试确认启用 RabbitMQ 时存在身份快照 InfoContributor。
- 模块验证覆盖 gateway 单元测试、RabbitMQ 集成测试和 Spring Boot 启动。
- 更新现场接入手册和消息链路文档，删除“当前无单调保护/无生效版本查询”的旧限制。

# 告警通知、升级与送达状态设计

## 1. 目标与边界

本批把现有告警中心从“平台内可见、人工确认和关闭”推进为“可配置触达、可靠升级、可追溯送达和事件工单闭环”。目标用户是矿区调度员、值班人员、设备管理员和现场运维人员；他们需要明确知道一条严重告警已经通知了谁、通过哪个渠道、当前停在哪个环节、是否需要人工重试或升级。

首批支持 SMTP 邮件、企业微信机器人、钉钉机器人、飞书机器人、阿里云短信、阿里云语音和通用 Webhook。真实账号、签名、模板、号码资质、客户网络与人员响应演练按当前决策延期，仓库只提供确定性自动化、模拟回执和可部署配置边界。

本批不把现有 `mine_work_order` 当成告警工单。该表表达矿山生产运输作业计划，生命周期、班次、路线和吨位语义都不适合事故处置。通知领域新增“告警事件单”，只负责告警分派、升级、处置和关闭，并通过 `alarm_id` 与告警周期关联。

## 2. 方案选择

候选方案有三种：

1. 告警消费者同步调用各渠道。实现快，但任何供应商超时都会拖慢 RabbitMQ 消费；进程崩溃后难以判断是否已经产生计费发送，也无法可靠升级。
2. 每个渠道直接使用 RabbitMQ 队列。吞吐扩展容易，但策略、步骤、尝试、回执和人工重试会分散到多个状态源，前端很难给出可信总览。
3. 平台自管通知控制面和投递账本。告警入库时只创建不可变通知意图与未来步骤，独立租约工作器执行外部调用，异步回执幂等推进最终状态。

采用方案 3。首版运行时部署在 `mine-server` 的独立线程池中，减少单矿区私有化部署复杂度；包边界、适配器 SPI、数据库租约和指标保持独立，后续可以无损迁移到单独 `mine-notification` 进程。HTTP 请求线程、告警 RabbitMQ 消费线程和通知投递线程互不复用。

## 3. 领域模型

### 3.1 渠道与接收对象

`notification_channel` 保存渠道名称、类型、供应商、启停状态、非敏感配置、加密凭据、超时和版本。凭据使用独立 AES-256-GCM 密钥文件加密，密文关联渠道标识与配置版本；API 永不返回密文或明文，只返回是否已配置和最后验证时间。

`notification_recipient_group` 和 `notification_recipient` 保存值班组及成员。成员类型为系统用户或外部联系人；手机号、邮箱和机器人地址按敏感级别加密，另存不可逆匹配摘要和脱敏展示值。策略只引用稳定接收组，不复制联系方式。

### 3.2 模板与升级策略

`notification_template` 使用渠道类型、语言和告警生命周期区分模板。模板变量只允许固定白名单，如告警编号、规则、等级、矿区、设备展示名、触发时间和处置链接；不执行任意脚本、SQL、SpEL 或动态对象访问。

`notification_policy` 是稳定策略聚合根，`notification_policy_version` 保存不可变草稿或已发布版本。一个版本包含匹配条件、确认后是否停止升级、恢复后是否通知以及有序步骤。每个步骤定义延迟、渠道、接收组、模板和是否创建事件单。发布时完成渠道、模板、接收组、步骤顺序和严重等级覆盖检查；运行中的告警始终绑定触发时发布版本，不受后续编辑影响。

### 3.3 事件、投递与回执

`notification_incident` 每个 `alarm_id + policy_version_id` 唯一，保存 OPEN、ACKNOWLEDGED、RECOVERED、CLOSED 或 EXHAUSTED 状态以及下一升级时间。

`notification_delivery` 表达一步中面向一个接收目标的一次逻辑投递，状态为 `PENDING`、`CLAIMED`、`SUBMITTED`、`DELIVERED`、`FAILED`、`UNKNOWN` 或 `CANCELLED`。`SUBMITTED` 仅表示供应商受理，不能展示为已送达。SMTP、机器人和通用 Webhook 没有终端级回执时最终保持 `SUBMITTED`，页面明确显示“渠道已受理/无终端回执”。

`notification_delivery_attempt` 追加保存每次外呼的开始、结束、固定错误码、供应商请求标识和脱敏摘要。`notification_receipt` 保存去重键、供应商消息标识、规范化结果、回执时间和有界原始载荷哈希。阿里云短信和语音回执允许重复和乱序，处理器使用供应商消息标识与回执去重键幂等更新，终态不得被更早状态回退。

## 4. 数据流与一致性

告警 `raised` 消息进入 Server 后，`sys_inbox_event`、`alarm_event`、匹配的 `notification_incident`、首批 `notification_delivery` 和审计事实在同一 PostgreSQL 事务提交。若告警已经存在，重复事件不会重复创建通知。未匹配任何已发布策略时告警仍正常落库，并增加“无通知策略”低基数指标。

通知工作器使用 `FOR UPDATE SKIP LOCKED` 有界认领到期投递，写入租约拥有者和到期时间后才调用适配器。适配器必须返回稳定结果：

- `SUBMITTED`：供应商接受，携带可用于回执关联的消息标识；
- `DELIVERED`：仅允许具备同步终端确认语义的渠道使用；
- `RETRYABLE_FAILURE`：网络、限流或供应商暂时失败；
- `PERMANENT_FAILURE`：号码、模板、认证或配置不可恢复；
- `UNKNOWN`：调用超时且无法判断供应商是否已受理，禁止盲目重发计费渠道。

可安全重试的失败使用有界指数退避和随机抖动。阿里云短信与语音没有原生幂等保证，超时进入 `UNKNOWN`，由回执或查询任务收敛，不能直接重复调用。Webhook 类渠道携带平台稳定幂等键；供应商不支持时仍由本地账本阻止并发重复。

调度器只生成已经到期的升级步骤。告警确认后，若绑定策略配置“确认即停止升级”，未来步骤原子取消；已提交投递和既有事件单保留证据。告警恢复可以按策略发送恢复通知，并停止尚未到期的触发升级。告警关闭要求事件单已经解决或操作者具有覆盖权限。

## 5. 事件工单

`notification_ticket` 是告警事件单，字段包含组织、矿区、告警、严重等级、标题、当前负责人、负责角色、SLA 到期时间和乐观锁版本。生命周期为 `OPEN -> ASSIGNED -> IN_PROGRESS -> RESOLVED -> CLOSED`，另允许 `OPEN/ASSIGNED -> CANCELLED`。所有状态变化写入不可变 `notification_ticket_history`。

升级步骤可以创建事件单、转派用户/角色或提升优先级，但同一事件单和步骤只能执行一次。值班员在通知中心查看事件单、领取、转派、开始处置、解决和关闭；每个写操作都要求 `Idempotency-Key`、权限和操作说明。事件单与生产作业单在菜单、API、权限、数据库和统计上完全分离。

## 6. 适配器与安全边界

`NotificationChannelAdapter` 只接收已经渲染、长度受控的标题/正文、脱敏目标的受控表示、渠道配置快照和稳定投递标识。适配器不能访问业务数据库、Sa-Token、RabbitMQ 或任意 Spring Bean。注册表按 `channelType + provider` 唯一发现适配器，重复键或元数据非法阻止通知工作器启动。

内置适配器：

- SMTP：STARTTLS/SMTPS、连接与读超时、受控发件人；成功表示服务器受理。
- 企业微信、钉钉、飞书机器人：固定官方域名或显式允许列表、HTTPS、签名、消息长度限制和平台幂等键。
- 阿里云短信：`SendSms`，保存 `BizId`，HTTP/MNS 回执推进送达状态。
- 阿里云语音：`SingleCallByTts`，保存 `CallId`，异步回执推进结果。
- 通用 Webhook：HTTPS、域名允许列表、DNS 重绑定防护、禁止环回/链路本地/云元数据地址、HMAC 签名。

所有日志、审计、指标和错误只使用渠道类型、供应商、状态和固定错误码等低基数标签。手机号、邮箱、Webhook 地址、模板正文、凭据、供应商异常原文和消息标识不得进入 Prometheus 标签或普通日志。

## 7. API、权限与前端

新增顶级菜单“通知与升级”，统一工作台包含运行总览、渠道与接收组、升级策略、送达记录和事件工单五个标签。视觉延续暖橙、矿石灰的工业控制台；首页先展示当前失败、未知、待升级和 SLA 超时结论，再渐进展开渠道配置和策略细节。状态必须同时使用文字、图标和 Naive UI 语义类型，不能只依赖颜色。

核心权限：

- `notification:overview:view`
- `notification:channel:view/edit/test`
- `notification:recipient:view/edit/sensitive`
- `notification:policy:view/edit/publish`
- `notification:delivery:view/retry/cancel`
- `notification:ticket:view/assign/resolve/close`

测试发送和人工重试属于外部副作用操作，必须二次确认、要求原因和幂等键。首批自动化测试只使用本地模拟适配器，不调用真实收费渠道。

## 8. 可观测性、故障与验收

指标覆盖事件创建、策略未匹配、投递状态、尝试结果、到期积压、租约失联、回执重复/未知、事件单 SLA 和渠道健康。Prometheus 告警覆盖严重告警无通知策略、待投递持续积压、`UNKNOWN` 增长、死信、回执长时间未收敛和事件单 SLA 超时。

渠道配置错误只禁用该渠道，不影响告警落库和平台内处置。数据库不可用时不进行外部发送；租约过期后只重新认领可安全重试的记录。恢复任务收敛失联 `CLAIMED`、到期步骤和未终结回执查询，所有扫描均有批次与时间上限。

自动化验收包括：数据库中文表/字段注释、约束和索引；策略发布与版本绑定；告警重复/乱序；认领、退避、未知结果和租约恢复；回执重复/乱序；确认停止升级；事件单幂等和乐观并发；RBAC、审计、密文边界；前端中英文、主题、窄屏、空/错/加载状态和 UI 治理。真实渠道送达、客户网络、资质、值班响应、容量、HA、备份恢复和长稳继续标记为 `DEFERRED`。

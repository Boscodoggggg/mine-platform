# 14 架构决策、术语与待确认事项

## 1. ADR 摘要

### ADR-001：自研平台，不做现有 IoT 平台二开

状态：已接受。

原因：核心差异在矿山业务、弱网、厂商私有协议、配置发布和现场运维。二开通用平台会受其数据模型、页面和升级节奏约束。

后果：需要自己承担设备安全、协议引擎、时序、监控、部署和升级的完整质量责任。

### ADR-002：单 RabbitMQ 集群、双 vhost

状态：已接受。

决定：/mine-device 承载 MQTT；/mine-platform 承载内部 AMQP。

后果：组件更少、运维简单；但共享集群内存、磁盘和故障域，必须有配额、背压和容量测试。

### ADR-003：不用 Kafka

状态：已接受。

决定：一期使用 RabbitMQ 队列/Streams 能力。只有实际吞吐、重放或长期日志需求证明不足时才引入 Kafka。

### ADR-004：不用 Nacos

状态：已接受。

决定：Compose DNS、内部 DNS、VIP 和静态主机清单；动态业务策略由自研配置中心处理。

### ADR-005：模块优先 MVC + 局部 DDD

状态：已接受。

后果：易理解、开发快；通过模块 API、事件和 ArchUnit 保持边界，复杂状态机使用领域模型。

### ADR-006：协议配置优先，Java 插件兜底

状态：已接受。

后果：常见协议可无代码接入；复杂协议仍需要开发。禁止任意脚本保证安全和可预测性。

### ADR-007：配置包原子发布

状态：已接受。

决定：物模型、协议、映射、告警等可独立编辑，但运行时按完整 ConfigPackage 发布。

### ADR-008：管理员直接发布

状态：已接受。

决定：不设审批流，但保留校验、样本回归、影响预览、二次确认、审计和回滚。

### ADR-009：PostgreSQL + TimescaleDB + Redis

状态：已接受。

决定：业务/配置在 PostgreSQL；历史遥测/UWB 在 TimescaleDB；最新值和 session 在 Redis。

### ADR-010：SoybeanAdmin + Naive UI

状态：已接受。

决定：只复用前端底座，矿山业务自研。

### ADR-011：Cesium 是可选可视化，不做建模

状态：已接受。

决定：上传外部模型、展示实时对象；无模型时 demo/网格降级。

### ADR-012：Docker Compose 单机 + 五节点

状态：已接受。

决定：五节点为推荐生产基线；单机允许生产但标记非高可用。

### ADR-013：一期人工确认数据库切换

状态：已接受的设计基线。

原因：避免为自动选主引入未掌握的协调组件。未来 RTO 要求变化再评估。

### ADR-014：Sa-Token + 五表 RBAC

状态：已接受。

决定：sys_menu 同时存目录、页面和按钮权限，不增加独立 permission 表。

### ADR-015：groupId 使用 com.bosco，项目采用 Apache-2.0

状态：已接受。

决定：所有 Maven 模块使用 `com.bosco` 作为 groupId，Java 基础包使用 `com.bosco.mine`；项目源码和自有文档采用 Apache License 2.0。

后果：根 LICENSE、NOTICE 和发行包许可证目录必须持续维护；SoybeanAdmin、Redis、Grafana、TimescaleDB 等第三方组件继续遵守各自许可证，不能因项目采用 Apache-2.0 而删除其声明。

## 2. 术语

| 术语 | 中文理解 |
|---|---|
| 遥测 Telemetry | 设备持续上报的状态和测量值 |
| 物模型 Thing Model | 平台对一类设备属性、事件和命令的标准定义 |
| 协议 Protocol | 原始网络报文如何拆帧、解析和编码 |
| 字段映射 Mapping | 厂商字段如何变成标准物模型属性 |
| 配置包 ConfigPackage | 一组相互兼容的不可变配置版本 |
| 发布 ConfigRelease | 将配置包应用到产品/组/设备的事实 |
| Last-known-good | 节点最后一次成功加载且可继续运行的配置 |
| 边缘代理 mine-edge | 可选车载/现场缓存和补传程序 |
| Broker | 接收、路由 MQTT/AMQP 消息的 RabbitMQ |
| vhost | RabbitMQ 内的逻辑隔离空间 |
| QoS | MQTT 投递服务等级；不等于业务执行成功 |
| 幂等 Idempotency | 重复处理同一请求不会重复产生副作用 |
| Outbox | 业务事务内记录待发事件，随后可靠投递 |
| Inbox | 消费端记录已处理事件防止重复副作用 |
| occurredAt | 数据在设备侧发生的时间 |
| receivedAt | 平台接收到数据的时间 |
| 迟到 Late data | 发生时间早于已经处理/显示的最新数据 |
| RPO | 故障时最多允许丢失的数据时间窗口 |
| RTO | 故障后允许的最长恢复时间 |
| 黄金样本 | 协议版本必须持续通过的固定回归报文 |
| 控制面 | 配置、管理和发布 |
| 数据面 | 连接、解析、处理和存储实时设备数据 |

## 3. 已知限制

- RabbitMQ 双 vhost 不是物理隔离。
- 单机没有主机级高可用。
- 基础能力设备没有 sequence 时只能有限去重。
- MQTT QoS 1 不能证明设备业务执行成功。
- 没有正式三维模型时不能呈现真实矿区精细场景。
- TimescaleDB OSS 基线不依赖受限功能，部分高级压缩/策略需要自研任务或重新评估许可证。
- 一期数据库故障切换需要运维确认。
- 硬件配置必须由真实负载报告确定。

## 5. 触发重新评估的条件

### 拆 RabbitMQ 集群

满足任一条件时评估设备 MQ 与内部 MQ 物理分离：

- 设备连接/重连导致内部命令和告警 SLA 无法满足。
- 集群内存/磁盘水位频繁互相影响。
- 安全域要求物理隔离。
- 压测证明单集群容量无法留足故障余量。

### 引入 Kafka

- 需要数日级高吞吐事件重放。
- 多个独立分析消费者反复读取全量流。
- RabbitMQ Streams 仍无法满足已量化吞吐/保留要求。

### 引入自动数据库选主

- 现场要求 RTO 明确低于人工切换能力。
- 运维团队能掌握并演练自动选主组件。
- 已解决网络分区和 fencing。

### 引入 Kubernetes

- 矿区内服务数量、发布频率和弹性需求显著增长。
- 有成熟 Kubernetes 运维团队。
- Compose 多主机发布成为可量化瓶颈。

## 6. 最终不可变原则

- 生产数据不因页面便利而牺牲可追溯性。
- 配置发布必须版本化、原子化、可回滚。
- 异步消息按至少一次设计，消费者必须幂等。
- 设备字段差异在协议/映射/物模型层解决，不扩散到业务页面。
- 危险命令宁可拒绝，也不在不确定状态下自动重试。
- 现场可以离线运行、安装、升级和恢复。

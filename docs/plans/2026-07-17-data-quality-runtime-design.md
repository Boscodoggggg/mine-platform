# Phase 2 数据质量策略运行消费设计

## 目标

把现有产品、设备组、单设备三级策略控制面扩展到 `DATA_QUALITY`，并让
`mine-telemetry` 在遥测入库前真正执行策略。第一版只做可追溯的质量降级，
不静默丢弃现场数据；所有违规都必须保留结构化证据和低基数指标。

本切片不执行真实设备、真实矿区网络、容量、HA、备份恢复和 24/72 小时长稳验证。

## 方案比较

### 方案 A：Telemetry 直连业务库

实现最短，但会把 `mine-server` 的表结构和数据库凭据泄漏给运行服务，破坏服务边界，
也无法独立扩缩容和演进，否决。

### 方案 B：每条遥测同步调用管理服务

可以拿到最新有效值，但把控制面可用性和延迟放进高频数据面；管理服务抖动会直接阻塞
遥测，否决。

### 方案 C：事务 Outbox + 轻量变更事件 + 版本化运行快照

管理事务只写不可变发布事实和 Outbox。Telemetry 收到轻量事件后，通过既有外部服务令牌
拉取有界、校验过的运行快照，在自身数据库中原子激活最后正确版本。遥测热路径只读取本地
持久镜像，不直连管理库，也不依赖同步 HTTP。

采用方案 C。它复用了协议配置已经验证过的事件、服务令牌、哈希和手工 ACK 模式，并能用
单调版本拒绝乱序覆盖。

## 第一版策略字段

| 字段 | 类型与范围 | 运行语义 |
|---|---|---|
| `staleAfterSeconds` | 整数，1～604800 | 设备时间早于接收时间超过阈值时，将现有值降级为 `UNCERTAIN` |
| `futureToleranceSeconds` | 整数，0～3600 | 设备时间超前超过容忍值时使用接收时间排序，并标记时间不可信 |
| `required.<propertyId>` | 布尔值 | 必填属性缺失时保留本帧其他数据，产生 `REQUIRED_MISSING` 证据并降级 |
| `minimum.<propertyId>` | 十进制数 | 数值低于下限时仅将该属性标记为 `BAD` |
| `maximum.<propertyId>` | 十进制数 | 数值高于上限时仅将该属性标记为 `BAD` |

字段仍按产品默认、设备组覆盖、单设备覆盖合并。局部片段和最终有效值都必须校验；任何最终
下限大于上限的组合都禁止发布或成员变更，不能把矛盾配置交给运行节点。

跳变检测需要可靠读取前值并处理乱序、补传和设备重启，序列缺口需要使用持久顺序状态；二者
在告警闭环切片中实现，不用一个不可靠的简化比较冒充生产能力。

## 数据流

1. 管理员创建、发布或回滚 `DATA_QUALITY` 版本。
2. 服务端在同一事务内固化发布事实、运行修订和 Outbox 事件。
3. 设备组成员、优先级或归档变化同样推进运行修订。
4. Outbox relay 在提交后向专用策略交换机发送持久化轻量事件并等待 Broker confirm。
5. Telemetry 手工 ACK 消费事件，拉取并校验运行快照，在自身数据库原子激活；瞬时失败重投，
   永久损坏进入死信。
6. 遥测批次按设备批量读取当前策略，在入库前完成时间、必填和范围判定。
7. 历史点、最新值、质量证据和摄取水位在同一数据库事务提交；随后刷新 Redis 和实时事件。

## 一致性与失败语义

- 运行修订按产品和策略类型单调递增；低修订不得覆盖高修订。
- 策略加载失败继续使用最后正确版本，不把未校验数据激活为当前策略。
- 未配置数据质量策略时保持既有行为，不能因为控制面暂时不可达而丢弃遥测。
- 质量证据以事件标识和规则编码幂等，RabbitMQ 重投不得重复生成证据。
- `BAD` 属性保留历史和证据，但不得驱动后续告警和派生计算；这一消费约束由后续告警引擎落实。
- 不把设备标识、属性标识或异常文本放入 Prometheus 标签，避免高基数和敏感信息泄漏。

## 可观测与验收

- 记录策略事件解码、拉取、校验、激活、持久化的成功/失败计数和耗时。
- 记录质量规则命中计数，标签只允许规则编码和结果。
- 对持续策略加载失败和质量异常突增提供 Prometheus 告警规则。
- 单元测试覆盖类型边界、继承矛盾、质量合并和证据生成。
- PostgreSQL/TimescaleDB 集成测试校验新表、约束、幂等、表注释和全部字段注释。
- RabbitMQ 集成测试覆盖确认、重投、死信和乱序修订拒绝。
